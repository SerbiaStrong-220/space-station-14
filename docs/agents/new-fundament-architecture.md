# Проектирование новых базисных систем

Базисная система — основа, которую будут использовать многие другие системы. Уже существующие примеры: `EntityEffectSystem`, `DamageableSystem`, `ExperienceSystem`. Это ориентиры по масштабу и API, а не то, что нужно создавать.

## Сначала проверь, нужна ли она
Прежде чем писать новую базисную систему, убедись, что существующие решения не подходят. Над ними уже поработали многие разработчики, их API устоялось и будет развиваться дальше. Если подходящее есть, используй его. Если нет, **опиши разработчику план (назначение, API, события, список новых типов с обоснованием каждого) и дождись подтверждения**, потом пиши код.

## Правила проектирования
- **Методы только под реальное использование.** Если метод никто не вызывает, не пиши его.
- **События-проверки допустимы заранее.** Систему будут использовать другие системы, поэтому не цементируй логику: перед каждым значимым действием поднимай событие, позволяющее другим запретить или изменить его (например `...AttemptEvent`). Подписчиков может не быть, это нормально. Это единственное исключение из правила выше.
- **API должен быть понятным.** Называй методы по паттерну `Try.../Resolve...` (см. [csharp-style.md](csharp-style.md)) и делай их удобными для вызова из других систем.
- **Типов столько, сколько требует API.** Базисная система соблазняет «заложить» абстракции. Не делай этого: интерфейс вводи, только когда уже есть или явно будут несколько реализаций, обёртки над коллекциями и примитивами не создавай (см. «Минимум типов» в [csharp-style.md](csharp-style.md)). Расширяемость обеспечивают события-проверки, а не иерархии типов.
- **Не собирай много компонентов в одной итерации.** Холодные компоненты не мешают горячим, но если в одном цикле нужно читать много разных компонентов, будут кэш-мисы. Держи горячие данные в одном-двух небольших компонентах, редкие данные выноси в отдельные.

## После написания
1. **Тесты.** В отличие от обычных систем (для них тесты не пишем), для базисной они нужны. Определи, что проверяет только твоя система, без проверки чужого функционала. Напиши такие тесты в `Content.Tests` (или `Content.IntegrationTests`, если нужен мир с сущностями), ориентируясь на существующие тесты рядом. Для проверки используй минимальные тестовые сущности, а не боевые прототипы. Запусти их узким фильтром (см. [build-test.md](build-test.md)).
2. **Комментарии.** Удали комментарии, которые повторяют название метода. Для публичных методов напиши краткое описание: зачем использовать, когда вызывать, какое событие-проверку метод поднимает.
```csharp
// ❌ Добавляет эффект.
// ✅ Накладывает эффект на сущность. Перед этим поднимает AddEffectAttemptEvent,
//    подписчики могут его отменить. Возвращает false, если наложение отменено.
public bool TryAddEffect(Entity<EffectHolderComponent> ent, EntProtoId effect)
```
